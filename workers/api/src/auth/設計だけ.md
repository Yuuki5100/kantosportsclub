# workers/api 認証・認可設計

最終更新: 2026-05-02

## 1. 目的

Spring Boot 側の `AuthController` / `AuthService` と、認可方式共通ルールを Workers API に移植するための設計メモ。

この文書は実装ではなく、`workers/api/src/auth/` 配下に置くべき責務と境界を整理する。

## 2. 参照元の要点

### 2-1. 認証

Spring 側では `AuthController` が HTTP 入口、`AuthService` が auth flow の振り分け役になっている。

- `AuthController`
  - `POST /api/auth/login`
  - `POST /api/auth/logout`
  - `GET /api/auth/status`
  - `GET /api/auth/external-login`
  - `GET /api/auth/callback`
  - `refresh` は現状コメントアウトされているが、設計上は独立した経路として扱う
- `AuthService`
  - `auth.type` を見て `AuthFlow` を切り替える

### 2-2. 認可

認可方式共通ルールでは、判定の正本と経路を次のように固定している。

- エンドポイント要求権限の正本は `endpoint_authority_mapping`
- ロール保有権限の正本は `role_permission`
- 最終判定は `statusLevelId` 比較
- 標準経路は fail closed
- `@RequirePermission` 未設定は拒否

### 2-3. 権限設定キャッシュ

Spring 側の `PermissionConfigProviderImpl` は、`endpoint_authority_mapping` を DB から読み込み、メモリ上に展開している。

- `@PostConstruct` で初回ロードする
- `@Scheduled` で定期再読込する
- 読み込み結果は不変マップとして保持する
- `METHOD /path` のキーに対して `AntPathMatcher` 相当でパターン一致させる
- 1 endpoint に複数 mapping がある場合は custom 権限として集約する
- `menuFunctionId -> requiredLevel` を `custom` として保持する
- `custom` の最大値を default level にする
- ロード結果はログ出力する

## 3. Workers 側の基本方針

### 3-1. 責務分離

Workers 側でも、HTTP 入口・認証フロー・権限判定を分離する。

- route
  - HTTP method / path / request body / response の責務だけを持つ
  - cookie の読み書きとステータスコードを扱う
- auth service
  - `auth.type` に応じて認証フローを振り分ける
  - login / refresh / logout / status / external-login / callback をまとめる
- auth repository
  - refresh token や session 相当の永続化を D1 で扱う
  - `users`、`role_permission`、`endpoint_authority_mapping` を参照する
- permission service
  - `METHOD /path` で要求権限を引き、role permission と比較する
  - 未定義は拒否する
- permission config provider
  - `endpoint_authority_mapping` を再読込してメモリキャッシュする
  - endpoint ごとの default level と custom level を提供する

### 3-2. Worker 前提

Workers には Java の `HttpSession` や Spring Security の `Authentication` が無い。

そのため、Spring のセッション依存部分は Worker では次のように置き換える。

- 認証状態の保持は Cookie ベースのトークン、または D1 の refresh token レコードを使う
- リクエスト時のユーザー判定は `c.req.header("Authorization")` または Cookie から行う
- 認可時の principal は Worker 内の claims / user row に置き換える

## 4. 想定エンドポイント

Spring と同じ利用形を維持する前提で、Workers でも `/api/auth` 配下にまとめる。

- `POST /api/auth/login`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `GET /api/auth/status`
- `GET /api/auth/external-login`
- `GET /api/auth/callback`

## 5. D1 の正本

認証・認可で必要になる正本は D1 に寄せる。

- `users`
- `roles`
- `permissions`
- `role_permission`
- `endpoint_authority_mapping`
- `auth_refresh_token` か同等の refresh token 管理表

補足:
- `endpoint_authority_mapping` は `METHOD /path` で引ける形にする
- `role_permission` は `role_id + permission_id` で引ける形にする
- `statusLevelId` をコード固定値にしない

## 6. 標準フロー

### 6-1. login

1. 認証方式を `auth.type` で判定する
2. 成功時は access token / refresh token / user 情報を返す
3. 必要なら Cookie を発行する

### 6-2. refresh

1. refresh token を Cookie またはヘッダから取得する
2. D1 で token の有効性と所有者を確認する
3. 新しい access token を返す
4. 失効済み token は拒否する

### 6-3. logout

1. 現在の refresh token を失効させる
2. Cookie を削除する
3. 200 系で終了する

### 6-4. status

1. 現在の認証状態を判定する
2. ユーザー情報と権限情報を返す
3. FE が初期表示で利用できる互換形を維持する

## 7. 認可フロー

Worker 側の認可は、次の順で判定する。

1. 認証済みか確認する
2. `PermissionConfigProvider` 相当のキャッシュから `METHOD /path` を引く
3. endpoint 定義の default level と custom level を解決する
4. `role_permission` を引いてユーザーの `statusLevelId` を確認する
5. 要求レベル以上なら許可する
6. 未定義、未認証、不足権限は拒否する

設計上の注意:
- 未マッピングのエンドポイントを暗黙許可しない
- `roleId` や `statusLevelId` をコードへ直書きしない
- 権限の比較は DB 正本に従う
- endpoint 定義の再読込方法を明示する
- pattern match は `METHOD /path` 文字列に対して行う
- endpoint 定義が空なら fail closed にする

## 8. Workers での配置案

```text
workers/api/src/auth/
  authController.ts
  authService.ts
  authRepository.ts
  authPermissionService.ts
  authCookie.ts
  authToken.ts
```

路由層から見た最小責務は次の通り。

- `authController.ts`
  - route 定義
  - request/response 変換
- `authService.ts`
  - flow の振り分け
  - login / refresh / logout / status
- `authRepository.ts`
  - D1 アクセス
- `authPermissionService.ts`
  - endpoint 権限判定
- `permissionConfigProvider.ts`
  - endpoint 権限定義のキャッシュ
  - DB 再読込
- `authCookie.ts`
  - Cookie 読み書き
- `authToken.ts`
  - token 検証と claims 処理

## 9. 実装時の判断基準

- Spring のレスポンス形に互換性が必要なら維持する
- Worker では session 依存を増やしすぎない
- 認証と認可を同じ関数に詰め込まない
- 旧 Spring のような権限キャッシュ層を持つ場合は、再読込周期を設計で決める
- キャッシュは読み取り専用の不変データとして扱う
