# workers/api 認証・認可設計

最終更新: 2026-05-03

## 1. 目的

Spring Boot 側の `AuthController` / `AuthService` と、認可方式共通ルールを Workers API に移植するための設計メモ。

本設計は、現在の `workers/api/src` 配下の構成に合わせて、認証・認可ロジック、D1 に登録する正本テーブル、権限制御、各ファイルの責務を整理する。

Spring 側では、`AuthController` が HTTP 入口、`AuthService` が認証フローの振り分け役になっていた。Workers 側でも同様に、HTTP route、service、repository、token、cookie、permission の責務を分離する。

## 3. 配置方針

当初案では `workers/api/src/auth/` 配下に `authController.ts`、`authService.ts`、`authRepository.ts`、`authPermissionService.ts`、`authCookie.ts`、`authToken.ts` を置く想定だった。

現在の構成では、責務ごとに既存ディレクトリへ分散して配置する。

| 旧設計上の責務 | 現在の配置 | 役割 |
|---|---|---|
| authController.ts | `routes/auth.ts` | HTTP method / path / request body / response / cookie / status code |
| authService.ts | `service/authService.ts` | 認証フローの振り分け、login / refresh / logout / status / external-login / callback |
| authRepository.ts | `repositories/authRepository.ts` | D1 アクセス、users / role_permission / endpoint_authority_mapping / refresh token |
| authPermissionService.ts | `service/authPermissionService.ts` | endpoint 権限判定、role permission 比較、fail closed |
| authCookie.ts | `service/authCookie.ts` | Cookie 読み書き、削除、refresh token の取得 |
| authToken.ts | `function/authToken.ts` | access token / refresh token / claims の生成・検証 |
| permissionConfigProvider.ts | `service/authPermissionService.ts` または将来分離 | endpoint_authority_mapping の読み込み・キャッシュ |

`auth/` ディレクトリは、認証モジュールの入口や設計メモを置く場所とする。

```text
auth/
  index.ts       # auth 関連の export 集約が必要な場合に利用
  設計だけ.md    # 本設計書
```

## 4. 各ファイルの責務

### 4-1. `routes/auth.ts`

Java / Spring でいう `AuthController` 相当。

責務:

- `/api/auth` 配下の route 定義
- request body の parse
- query parameter の取得
- Authorization header の取得
- Cookie の取得・設定・削除
- `authService` の呼び出し
- HTTP status code の決定
- FE に返す response 形式の整形

想定 route:

```text
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/auth/status
GET  /api/auth/external-login
GET  /api/auth/callback
```

やらないこと:

- password 検証ロジックを直接書かない
- DB に直接アクセスしない
- role_permission を直接比較しない
- endpoint_authority_mapping を直接読まない
- token の署名・検証処理を書かない

---

### 4-2. `service/authService.ts`

Spring の `AuthService` 相当。

責務:

- `auth.type` に応じた認証フローの切り替え
- `login`
- `refresh`
- `logout`
- `status`
- `external-login`
- `callback`
- repository / token / cookie / permission service の調停
- FE が期待する user 情報・権限情報の組み立て

認証方式は `auth.type` を見て切り替える。

例:

```text
auth.type=password
auth.type=external
auth.type=mock
```

ただし、route 層は `auth.type` を意識しない。  
route 層は常に `authService.login()` などの facade を呼び出す。

---

### 4-3. `repositories/authRepository.ts`

D1 アクセスの責務を持つ。

責務:

- `users` 参照
- `roles` 参照
- `permissions` 参照
- `role_permission` 参照
- `endpoint_authority_mapping` 参照
- `auth_refresh_token` 登録・取得・失効
- login / refresh / status / authorization に必要な row を返す

やらないこと:

- HTTP response を返さない
- Cookie を操作しない
- JWT を生成しない
- endpoint 権限の最終判定をしない

---

### 4-4. `service/authPermissionService.ts`

認可判定の中心。

責務:

- `METHOD /path` から endpoint 要求権限を取得する
- `endpoint_authority_mapping` を読み込む
- endpoint ごとの default level / custom level を解決する
- user の role から `role_permission` を取得する
- `statusLevelId` を比較する
- 未定義・未認証・不足権限を拒否する

Spring 側の `PermissionConfigProviderImpl` に近い責務も、現時点ではこのファイルへ含める。

将来的に肥大化する場合は、次のように分離してもよい。

```text
service/
  authPermissionService.ts
  permissionConfigProvider.ts
```

---

### 4-5. `service/authCookie.ts`

Cookie 操作の責務を持つ。

責務:

- refresh token Cookie の読み取り
- refresh token Cookie の設定
- refresh token Cookie の削除
- Cookie 属性の統一

Cookie 属性の例:

```text
HttpOnly
Secure
SameSite=Lax
Path=/api/auth
Max-Age=refresh token lifetime
```

Workers には Java の `HttpSession` がないため、セッション相当の状態は Cookie と D1 の refresh token レコードで扱う。

---

### 4-6. `function/authToken.ts`

token 処理の責務を持つ。

責務:

- access token の生成
- access token の検証
- refresh token 文字列の生成
- claims の encode / decode
- 有効期限の管理

access token を JWT にするか、D1 session ID 形式にするかは未確定。  
ただし route / service からは `authToken.ts` 経由で扱い、実装方式の差を隠蔽する。

---

### 4-7. `db/d1.ts`

D1 接続・DB ヘルパーの責務を持つ。

責務:

- D1 binding の取得
- 共通 query helper
- transaction 相当の処理が必要な場合の補助
- repository から使う DB アクセス共通処理

---

### 4-8. `env.ts`

Workers の環境変数・binding 型定義を持つ。

想定:

```ts
export type Env = {
  DB: D1Database;
  AUTH_TYPE?: string;
  JWT_SECRET?: string;
  COOKIE_SECURE?: string;
  PERMISSION_CONFIG_CACHE_TTL_SECONDS?: string;
};
```

---

### 4-9. `middleware/requestId.ts`

request id の付与を行う。

認証・認可ログを出す場合、request id と紐づけて追跡できるようにする。

## 5. 参照元 Spring 側の要点

### 5-1. 認証

Spring 側では、次のような役割分担だった。

- `AuthController`
  - HTTP 入口
  - `POST /api/auth/login`
  - `POST /api/auth/logout`
  - `GET /api/auth/status`
  - `GET /api/auth/external-login`
  - `GET /api/auth/callback`
  - `refresh` はコメントアウトされていたが、Workers 側では独立 route として扱う
- `AuthService`
  - `auth.type` を見て `AuthFlow` を切り替える

Workers 側でも同じ考え方で、`routes/auth.ts` は薄く保ち、`service/authService.ts` が flow を振り分ける。

---

### 5-2. 認可

認可方式共通ルールでは、判定の正本と経路を次のように固定する。

- endpoint が要求する権限の正本は `endpoint_authority_mapping`
- role が保有する権限の正本は `role_permission`
- 最終判定は `statusLevelId` 比較
- 標準経路は fail closed
- 未設定 endpoint は拒否する
- Spring の `@RequirePermission` 未設定拒否と同じ考え方を Workers に移す

Workers には annotation がないため、`METHOD /path` と `endpoint_authority_mapping` を対応させる。

---

### 5-3. 権限設定キャッシュ

Spring 側の `PermissionConfigProviderImpl` は、`endpoint_authority_mapping` を DB から読み込み、メモリ上に展開していた。

Workers 側でも同様の設計を踏襲する。

要件:

- 初回リクエスト時、または Worker 起動後の初回利用時にロードする
- 一定期間ごとに再読込できるようにする
- 読み込み結果は読み取り専用の不変データとして扱う
- `METHOD /path` のキーに対して pattern match する
- Java の `AntPathMatcher` 相当の path pattern match を行う
- 1 endpoint に複数 mapping がある場合は custom 権限として集約する
- `menuFunctionId -> requiredLevel` を `custom` として保持する
- `custom` の最大値を default level にする
- ロード結果はログ出力する
- 読み込み結果が空の場合は fail closed とする

---

## 6. D1 の正本テーブル

認証・認可で必要になる正本は D1 に寄せる。

必須テーブル:

```text
users
roles
permissions
role_permission
endpoint_authority_mapping
auth_refresh_token
```

補足:

- `endpoint_authority_mapping` は `METHOD /path` で引ける形にする
- `role_permission` は `role_id + permission_id` で引ける形にする
- `statusLevelId` はコード固定値にしない
- 認可判定は DB 正本に従う
- Worker 側のソースコードに roleId / permissionId / statusLevelId を直書きしない

## 7. テーブル設計案

### 7-1. `users`

ログイン対象ユーザーの正本。

```sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT,
  display_name TEXT,
  email TEXT,
  role_id TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'ACTIVE',
  locked_until TEXT,
  last_login_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

役割:

- login 時の user 検索
- password hash 検証
- account lock 判定
- status 判定
- role_id 取得

注意:

- password は平文保存しない
- `status` が `ACTIVE` 以外ならログイン拒否
- `locked_until` が未来ならログイン拒否

---

### 7-2. `roles`

role の正本。

```sql
CREATE TABLE IF NOT EXISTS roles (
  id TEXT PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

役割:

- user が持つ role の意味を管理する
- role_permission の親になる

---

### 7-3. `permissions`

権限の正本。

```sql
CREATE TABLE IF NOT EXISTS permissions (
  id TEXT PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  menu_function_id TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

役割:

- 権限コードの正本
- menu function と permission の対応
- endpoint_authority_mapping / role_permission から参照される

---

### 7-4. `role_permission`

role が保有する権限と level の正本。

```sql
CREATE TABLE IF NOT EXISTS role_permission (
  role_id TEXT NOT NULL,
  permission_id TEXT NOT NULL,
  status_level_id INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (role_id, permission_id),
  FOREIGN KEY (role_id) REFERENCES roles(id),
  FOREIGN KEY (permission_id) REFERENCES permissions(id)
);
```

役割:

- role ごとの保有権限を管理する
- `status_level_id` により、参照・更新・管理などの強さを表す
- endpoint が要求する level と比較される

判定:

```text
user role の status_level_id >= endpoint の required_level
```

なら許可。

---

### 7-5. `endpoint_authority_mapping`

endpoint が要求する権限の正本。

```sql
CREATE TABLE IF NOT EXISTS endpoint_authority_mapping (
  id TEXT PRIMARY KEY,
  http_method TEXT NOT NULL,
  path_pattern TEXT NOT NULL,
  permission_id TEXT NOT NULL,
  required_level INTEGER NOT NULL,
  menu_function_id TEXT,
  enabled INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (permission_id) REFERENCES permissions(id)
);

CREATE INDEX IF NOT EXISTS idx_endpoint_authority_mapping_method_path
ON endpoint_authority_mapping (http_method, path_pattern);

CREATE INDEX IF NOT EXISTS idx_endpoint_authority_mapping_permission
ON endpoint_authority_mapping (permission_id);
```

役割:

- `METHOD /path` に対して必要な permission と required level を定義する
- Workers の認可判定で最初に参照される
- 未定義 endpoint は拒否する

例:

```sql
INSERT INTO endpoint_authority_mapping (
  id,
  http_method,
  path_pattern,
  permission_id,
  required_level,
  menu_function_id,
  enabled
) VALUES (
  'eam_notice_get',
  'GET',
  '/api/notices/*',
  'permission_notice',
  1,
  'notice',
  1
);
```

複数 mapping:

1 endpoint に複数の `endpoint_authority_mapping` がある場合、custom 権限として扱う。

```text
GET /api/notices/{id}
  notice.read    required_level=1
  notice.update  required_level=2
```

この場合:

- `custom[menuFunctionId] = requiredLevel` として保持する
- default level は custom の最大値とする
- 判定時に対象の menuFunctionId が分かる場合は custom level を優先する
- 分からない場合は default level を使う

---

### 7-6. `auth_refresh_token`

refresh token の正本。

```sql
CREATE TABLE IF NOT EXISTS auth_refresh_token (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  expires_at TEXT NOT NULL,
  revoked_at TEXT,
  user_agent TEXT,
  ip_address TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)
);

CREATE INDEX IF NOT EXISTS idx_auth_refresh_token_user_id
ON auth_refresh_token (user_id);

CREATE INDEX IF NOT EXISTS idx_auth_refresh_token_expires_at
ON auth_refresh_token (expires_at);
```

役割:

- refresh token の有効性を D1 で管理する
- logout 時に `revoked_at` を設定する
- refresh 時に `expires_at` と `revoked_at` を確認する

注意:

- refresh token は平文保存しない
- DB には hash 化した token を保存する
- 失効済み token は拒否する

## 8. endpoint_authority_mapping のキャッシュ設計

### 8-1. キャッシュの目的

毎リクエストごとに `endpoint_authority_mapping` を全件読みに行くと、D1 アクセスが増える。

そのため、Workers 側でも Spring の `PermissionConfigProviderImpl` 相当のキャッシュを持つ。

---

### 8-2. キャッシュ内容

キャッシュは endpoint ごとの権限定義を保持する。

```ts
type EndpointPermissionConfig = {
  method: string;
  pathPattern: string;
  defaultLevel: number;
  custom: Record<string, number>;
  permissionIds: string[];
};
```

読み込み時に `endpoint_authority_mapping` を group 化する。

```text
key = METHOD + ' ' + path_pattern
```

例:

```text
GET /api/notices/*
POST /api/notices
PUT /api/notices/*
DELETE /api/notices/*
```

---

### 8-3. default level と custom level

1 endpoint に 1 mapping の場合:

```text
defaultLevel = required_level
custom = { menuFunctionId: required_level }
```

1 endpoint に複数 mapping の場合:

```text
custom[menuFunctionId] = required_level
defaultLevel = max(custom values)
```

理由:

- endpoint が複数権限を要求する場合、最も強い level を default とする
- ただし画面・機能単位で細かく見る場合は custom を参照できるようにする

---

### 8-4. path pattern match

判定時は次の文字列で比較する。

```text
METHOD /path
```

例:

```text
GET /api/notices/123
```

DB 側の `path_pattern` は次のような形式を想定する。

```text
/api/notices/*
/api/notices/:id
/api/notices/{id}
/api/notices/**
```

Workers 側では `AntPathMatcher` 相当の pattern match を実装する。

最低限対応すべき pattern:

| pattern | 意味 |
|---|---|
| `*` | 1 segment または任意文字列 |
| `:id` | path parameter |
| `{id}` | path parameter |
| `/**` | 配下すべて |

実装初期は Hono の route pattern と合わせて、`:id` 形式に寄せてもよい。  
ただし DB 正本としては Spring 互換の `{id}` や `*` が残る可能性があるため、変換層を持つ。

---

### 8-5. 再読込

Workers では Java の `@PostConstruct` や `@Scheduled` がない。

代替案:

1. 初回リクエスト時に lazy load
2. cache TTL を超えたら再読込
3. 管理用 endpoint から手動 refresh
4. deploy 時に初期化

初期方針:

```text
初回アクセス時にロード
TTL を過ぎたら次回アクセス時に再ロード
```

例:

```text
PERMISSION_CONFIG_CACHE_TTL_SECONDS=300
```

読み込み失敗時:

- 既存 cache があれば既存 cache を使う
- 既存 cache がなければ fail closed
- 読み込み結果が空なら fail closed
- エラーは request id 付きでログ出力する

## 9. 認証フロー

### 9-1. login

対象 route:

```text
POST /api/auth/login
```

流れ:

1. `routes/auth.ts` が request body から `username` / `password` を取得する
2. `authService.login()` を呼ぶ
3. `authService` が `auth.type` を確認する
4. `authRepository` が `users` から user を取得する
5. user status / locked_until を確認する
6. password hash を検証する
7. access token を発行する
8. refresh token を発行する
9. refresh token hash を `auth_refresh_token` に保存する
10. refresh token を HttpOnly Cookie に設定する
11. user 情報と permissions を response する

成功時 response 例:

```json
{
  "success": true,
  "accessToken": "...",
  "user": {
    "id": "user_001",
    "username": "user01",
    "displayName": "ユーザー01",
    "roleId": "role_user"
  },
  "permissions": [
    {
      "permissionId": "permission_notice",
      "statusLevelId": 1
    }
  ]
}
```

失敗時:

| 条件 | HTTP status |
|---|---|
| body 不正 | 400 |
| user 不存在 | 401 |
| password 不一致 | 401 |
| account locked | 423 |
| status inactive | 403 |

---

### 9-2. refresh

対象 route:

```text
POST /api/auth/refresh
```

流れ:

1. `authCookie` が refresh token を Cookie から取得する
2. Cookie がなければ Authorization header も確認する
3. token を hash 化する
4. `authRepository` が `auth_refresh_token` を取得する
5. `expires_at` を確認する
6. `revoked_at` が null であることを確認する
7. user を取得する
8. 新しい access token を発行する
9. 必要であれば refresh token rotation を行う
10. user 情報と permissions を response する

失効済み token は必ず拒否する。

---

### 9-3. logout

対象 route:

```text
POST /api/auth/logout
```

流れ:

1. Cookie または header から refresh token を取得する
2. token hash を作る
3. `auth_refresh_token.revoked_at` を現在時刻で更新する
4. refresh token Cookie を削除する
5. 200 系で終了する

response 例:

```json
{
  "success": true
}
```

---

### 9-4. status

対象 route:

```text
GET /api/auth/status
```

流れ:

1. Authorization header または access token Cookie を確認する
2. access token を検証する
3. claims から user id / role id を取得する
4. user が現在も有効か確認する
5. role_permission を取得する
6. FE 初期表示用の user / permissions を返す

未認証の場合も、FE が扱いやすい形で返す。

```json
{
  "authenticated": false,
  "user": null,
  "permissions": []
}
```

---

### 9-5. external-login

対象 route:

```text
GET /api/auth/external-login
```

流れ:

1. `authService.externalLogin()` を呼ぶ
2. external provider の authorization URL を生成する
3. URL または redirect response を返す

現時点で外部認証が未実装の場合は、501 または設定なし response とする。

---

### 9-6. callback

対象 route:

```text
GET /api/auth/callback
```

流れ:

1. query から `code` / `state` を取得する
2. external provider に token exchange を行う
3. external user を解決する
4. users と紐づける
5. access token / refresh token を発行する
6. Cookie を設定する
7. FE が扱える response へ整形する

---

## 10. 認可フロー

Workers 側の認可は、次の順で判定する。

1. 認証済みか確認する
2. `METHOD /path` を作る
3. `authPermissionService` が endpoint config cache から該当 mapping を探す
4. endpoint 定義の `defaultLevel` と `custom` を解決する
5. user の `role_id` を取得する
6. `role_permission` から user role の保有権限を取得する
7. `statusLevelId` を比較する
8. 要求レベル以上なら許可する
9. 未定義、未認証、不足権限は拒否する

判定式:

```text
role_permission.status_level_id >= endpoint_authority_mapping.required_level
```

---

## 11. fail closed ルール

標準経路は fail closed とする。

拒否する条件:

- 未認証
- access token 不正
- user が存在しない
- user が inactive
- role が存在しない
- endpoint_authority_mapping に該当なし
- endpoint_authority_mapping が disabled
- endpoint 定義が空
- role_permission に該当 permission がない
- statusLevelId が requiredLevel 未満
- cache 未ロードかつ DB 読み込み失敗
- DB 読み込み結果が空

重要:

```text
未マッピングの endpoint を暗黙許可しない
```

Spring の `@RequirePermission` 未設定拒否と同じ考え方で、Workers では `endpoint_authority_mapping` 未設定拒否とする。

## 12. 認可 middleware の考え方

認証・認可を全 route に手作業で書かないため、middleware 化する。

配置候補:

```text
middleware/authRequired.ts
middleware/permissionRequired.ts
```

ただし現在の構成では未作成のため、初期実装では `routes/*` から `authPermissionService` を呼び出してもよい。

推奨方針:

```text
1. 公開 route は明示的に public とする
2. それ以外は permission check を通す
3. endpoint_authority_mapping に存在しない route は拒否する
```

公開 route 例:

```text
GET  /api/health
POST /api/auth/login
POST /api/auth/refresh
GET  /api/auth/external-login
GET  /api/auth/callback
```

保護 route 例:

```text
GET    /api/notices
POST   /api/notices
PUT    /api/notices/:id
DELETE /api/notices/:id
GET    /api/boardgames
POST   /api/boardgames
```

公開 route も DB に登録するかどうかは設計判断が必要。  
fail closed を徹底するなら、public endpoint も `endpoint_authority_mapping` とは別の `public_endpoint_mapping` で管理するか、コード上で public route を明示する。

## 14. FE ログイン画面との接続

現在のログイン画面は、`loginUser(username, password)` を呼び出す前提。

Workers 側では、`POST /api/auth/login` で次の body を受け取る。

```json
{
  "username": "user01",
  "password": "password"
}
```

そのため、`routes/auth.ts` では `username` / `password` の存在チェックを行い、実際の認証は `authService.login()` に委譲する。

FE 側が期待する可能性が高い response:

```json
{
  "success": true,
  "accessToken": "...",
  "user": {
    "id": "...",
    "username": "...",
    "displayName": "...",
    "roleId": "..."
  },
  "permissions": []
}
```

login 失敗時は、FE が snackbar に出せる message を返す。

```json
{
  "success": false,
  "message": "ログインに失敗しました"
}
```

account lock 時は、Spring 側互換を意識して message を分ける。

## 19. 権限 level の考え方

`statusLevelId` / `required_level` は DB 正本で管理する。

- failure reason
- request id

## 21. 実装時の判断基準

- Spring の response 形に互換性が必要なら維持する
- Worker では session 依存を増やしすぎない
- 認証と認可を同じ関数に詰め込まない
- 旧 Spring のような権限キャッシュ層を持つ場合は、再読込周期を設計で決める
- キャッシュは読み取り専用の不変データとして扱う
- 未マッピング endpoint は暗黙許可しない
- roleId / statusLevelId / permissionId をコードに直書きしない
- 権限の比較は DB 正本に従う
- endpoint 定義が空なら fail closed にする

## 23. まとめ

Workers API では、Spring と同じく次の方針で認証・認可を移植する。

```text
HTTP route
  ↓
authService
  ↓
authRepository / authToken / authCookie
  ↓
D1 正本
```

認可は次の正本を使う。

```text
endpoint_authority_mapping  # endpoint が要求する権限
role_permission             # role が保有する権限
```

最終判定は常に次の比較で行う。

```text
role_permission.status_level_id >= endpoint_authority_mapping.required_level
```

標準経路は fail closed とし、未マッピング endpoint、未認証、不足権限、DB 定義なしは拒否する。

現在のディレクトリ構成では、Controller は `routes/auth.ts`、認証 facade は `service/authService.ts`、D1 アクセスは `repositories/authRepository.ts`、権限制御は `service/authPermissionService.ts` に配置する。
